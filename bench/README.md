# GC benchmark suite

Measures and stresses the performance of a LO garbage collector, and compares collectors
on identical programs. Standard-library Python plus the `gc-time` cargo feature; no other
dependencies.

## Why the runtime times itself

Process wall time contains the program's own work, process start-up and the OS. Most LO
programs spend far more time in the mutator than in the collector, so wall time hides
collector differences (the 22 public stress programs run 30-90 ms each and spend 1-15 ms
in the collector). With `--features gc-time` every call to `collect` is bracketed by a
clock read, and an `atexit` hook prints one line:

```
[lo-gc-time] collections=<n> total_ns=<sum> max_ns=<longest single pause>
```

`total_ns` is the collector's cost; `max_ns` is the worst pause. Native only: a wasm32
module has no clock import or exit hook, so there the feature compiles to no-ops.
Measured overhead of the timer is under about 3% of wall time (check V5 in every report).

## What is benchmarked

`python3 bench/bench.py list` prints the matrix. Six families, each swept over a live-set
or depth parameter, each run at the default 16 MiB heap and at 8 MiB:

| family | what it stresses |
|---|---|
| `churn` | garbage only. The floor: fixed cost per collection. |
| `live_list` | a live linked list while garbage is churned. Copying collectors pay for the live set on every collection. |
| `live_tree` | the same with a binary tree (two pointers per node). |
| `queue_window` | a sliding window of K nodes: each node dies K allocations after birth. Sweeps K across the nursery size, so nodes go from dying young to being promoted and then dying in tenured space (nepotism, major collections). |
| `old_to_young` | M long-lived holders overwritten round-robin with fresh objects: write barrier and remembered set on the hot path. |
| `deep_roots` | recursion D frames deep with a root per frame, garbage churned at the bottom: every collection scans D frames. |

Programs are generated by `bench.py`, so sizes are parameters, not hand-edited files.
`--scale F` multiplies iteration counts (never live-set sizes) for longer or shorter runs.
Depth is capped at 1000 so every benchmark also runs on wasm32.

## Running

On an x86-64 Linux host (linking needs `cc` and GNU ld):

```
cargo build --release --lib --features gc-time            # in rust/ ; and without the feature for the overhead check
python3 bench/bench.py run --compiler PATH/TO/lo-compiler \
    --runtime diddy=rust/target/release/liblo_runtime.a \
    --out bench/results/run-1
python3 bench/bench.py report bench/results/run-1
```

`--runtime LABEL=TIMED[:PLAIN]` can be given several times to compare collectors; `PLAIN`
is an archive built without `gc-time`, used only to measure the timer's overhead.
`--reps` (default 11) sets repetitions; `--plain-reps` (default 3) the repetitions of plain
builds; `--only REGEX` selects benchmarks.

Anywhere else (for example Apple Silicon) use Docker, which exports each runtime from a
git ref, builds the compiler and the archives inside an x86-64 container, and runs the
suite:

```
bench/docker.sh --all -- /path/to/lo-compiler            # all four collectors, 11 reps
bench/docker.sh [--reps N] [--scale F] [--only REGEX] [--out DIR] \
    cheney=origin/main markcompact=origin/feat/mark-compact-gc --diddy -- /path/to/lo-compiler
```

`--all` compares the four collectors: the Cheney reference (`origin/main`), mark-compact
(`origin/feat/mark-compact-gc`), the earlier generational collector (`origin/generational`)
and the diddy collector (`HEAD`). Run `git fetch` first.

`--diddy` is shorthand for `diddy=HEAD`: it adds the *diddy collector*, the generational
collector of the branch checked out in this repository, under the label `diddy`. Any
`LABEL=GITREF` works the same way.

To compare against an older or alternative collector, `bench/add-gc-timing.py RUST_DIR`
gives it the same timer (it wraps the one `unsafe fn collect` in `src/gc.rs`; `docker.sh`
calls it automatically for refs that lack the feature). On Apple Silicon the container
runs under Rosetta: relative comparisons are meaningful, absolute times are not those of
real x86 hardware.

## Output

In the `--out` directory:

* `runs.csv`: **one row per run** (program, family, heap, runtime, build, rep, exit code,
  output check, wall ms, collections, GC total ms, longest pause ms).
* `summary.csv`: **one row per cell** (program x heap x runtime x build): medians, min, max and
  coefficient of variation of GC time and wall time, GC share of wall time, exit code,
  output verdict (`OK`, `OOM`, `WRONG`). Open this in a spreadsheet.
* `report.md`: validity checks, a table per benchmark family, and a summary.
* `meta.json`: date, CPU, repetitions, and the sha256 of every archive that ran.

## How to tell the result can be trusted

Every report starts with validity checks; read them before the numbers.

* **V1** every program's stdout equals an expected value computed in Python from the
  program's parameters (32-bit wraparound included), not another collector's output. An
  out-of-memory exit (137) is reported as OOM, not as failure.
* **V2** collection counts are identical across repetitions. They are deterministic for a
  single-threaded program, so any variation means the harness is broken.
* **V3/V4** GC time never exceeds wall time, and the longest pause never exceeds total GC time.
* **V5** the timer's overhead (needs plain archives).
* **V6** run-to-run noise (coefficient of variation) of GC and wall time. Cells under about
  1 ms of GC are dominated by clock jitter; compare ratios only where there are several ms.
* Repetitions are interleaved across runtimes, so slow drift hits all of them equally; the
  archive hashes in the report show exactly which binaries were measured.

## Limits

* One mutator thread, one process, small programs: results say how a collector behaves on
  these allocation patterns, not on arbitrary programs.
* No GC timing on wasm32 (no clock); WASM comparisons can only use wall time.
* Wall time includes `fork`/`exec` (a few ms); GC time does not.
